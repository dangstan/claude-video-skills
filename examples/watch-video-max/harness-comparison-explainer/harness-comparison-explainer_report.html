02The finding that is not about speed

He builds a website with a DeepSeek model in DeepSeek Harness. It matches his brand guidelines, has the right feel, and has a visible defect. His explanation is the most important thing in eighteen minutes:

"This is where something that Codex or Claude Code would have never let happen, because of the verification checks, and because of the ability to screenshot, look, reason, iterate. There's a lot of things when it comes to UI and design that the DeepSeek models will not be very good at because it can't screenshot, it can't look."

And he attributes it correctly: "that doesn't mean DeepSeek Harness couldn't be good at design. It just means that the models you're putting inside there, you have to be aware of what their strengths and weaknesses are."

A verification loop needs a modality, not just a rule. Generate-screenshot-compare-correct is only available to a harness whose model can see the screenshot. A harness can ship the loop and be structurally unable to run it, because the capability lives in the model. This is the one axis where harness and model cannot be separated — and it is the hard floor under every "everything is a plugin" pitch in this batch.

03Why the harness can be changed at all

His analogy is the clearest statement of the open/closed harness split anywhere in these thirteen videos:

A closed harness like Claude Code is "a car we can sit in, we can drive it, we can change out the model of the engine, but we can't move things around." The open harness lets you "switch out the seats, switch out the steering wheel... change the way the agent actually behaves under the hood."

In DeepSeek Harness everything is a plugin — not just skills and MCP servers, but tools, skills, sessions, sandboxes, storage, the loops, and the UI. Both harnesses let you swap the model. Only one lets you swap the loop. Since the loop is where verification lives, an open harness is the only place a user can add verification the vendor did not ship — and equally the only place a user can remove verification the vendor did.

Four runtime modes

ModeWhat it is
standardFull coding agent — file editing, shell, web search. On "hi, who am I?" it immediately performs a context injection: reads AGENTS.md, CLAUDE.md and CLAUDE.local.md, then the DeepSeek system prompt, then the skill catalog.
PTCParallel / multi-chain. He compares it to Claude Code's dynamic workflows — "not exactly that."
minimalTwo-tool coding agent with persistent bash. No context injection at all. "Fast. Feels cheap."
creatorAuthor plugins, build agent presets, change the UI from inside the running application.

Two things fall out of the standard-versus-minimal comparison. The harness reads Claude Code's own context files unmodified — the de-facto format has become portable across competing harnesses. And the mode selector is a context-budget dial exposed to the user: the same agent with or without its standing instructions, chosen per task. That idea is worth having whatever tool you use.

04Cost, correctly framed

"If it's not an efficient harness, or if the model is so bad that it's not running efficiently, then ultimately that's not really that cheap. Those million-input, million-output numbers can be deceiving, because it's also about efficiency and cost to completion rather than just cost for tokens."

This is the right unit and almost nobody uses it. Price per million tokens compares models and is meaningless across harnesses, because the harness sets how many tokens a task consumes — and the timings above are the evidence.

The practical constraint, stated twice and easy to miss: you cannot use a Claude or Codex subscription by default. It is per-token API billing. The harness is free; switching to it converts a fixed monthly cost into a variable one.

05What preview-quality means

The application labels itself a developer preview and behaves like one: it stopped working outright on occasion; long sessions produced compaction bugs and context regressions — "it completely forgot what I was talking about"; creator mode flipped back instantly when selected, requiring a restart; and one incident locked his mouse into a small square, which he had Codex diagnose.

Against that, the trajectory view is genuinely good: granular intermediate steps for the whole session in one place, downloadable as a log. What he identifies it as for is better than the feature itself — "did you see what happened in this session? Can we build a plugin to fix X, Y and Z that just happened, so that next time your harness agentic loop runs, this doesn't happen." That closes a loop nothing else here closes: the trace of a failure becomes the input to a change in the machinery that produced it. It needs both the trace and the mutability.

And the warning he gives unprompted. "If people are giving out all these open source plugins, you don't know what might be in there. Have Claude Code or Codex review the plugins before you ever install anything off the internet." Note what the architecture makes of that: when the loops and the storage are plugins, an installed plugin is not an extension in a sandbox — it is a replacement for part of the agent's control flow. The blast radius is larger than in a conventional plugin system, and the mitigation on offer is advice, not a mechanism.

07Verdict

The most useful video in the batch, because it is the only one that measures anything. Watch it for the method: identical prompts, identical model, two harnesses, results shown on screen. The speed gap is large and survives its confounds. The quality gap does not — the skills were written for one of the two contestants, and the tester says so.

The finding that outlives both is the one about screenshots. A verification loop is not a policy you adopt; it is a capability you either have or do not.

Follow-up worth chasing: PTC mode, which he compares to dynamic workflows and never demonstrates; and whether a skill authored for DeepSeek Harness closes the quality gap, which is the obvious next experiment and the one he identifies himself.
